# ADR-0006: 本番のデプロイのジョブは、承認待ちの古いジョブを新しいジョブで自動で取り消す

- ステータス: Accepted
- 日付: 2026-11-18
- 関連: #411, ADR-0003（決定 3 の本番ジョブの `queue: max` を置き換える）, NatuEve_API ADR-0040

## コンテキストと課題

ADR-0003 決定 3 では、本番ジョブ（`deploy-production`）のジョブ単位の `concurrency` を `cancel-in-progress: false` と `queue: max` にした。
グループに入る順が入れ替わったとき、最新のコミットのジョブが古いコミットのジョブに取り消されないようにするためである。

運用すると、`queue: max` では承認待ちが溜まり続けた。
2026-11-13〜18 に main へのマージが 14 件続いた間、本番ジョブは 1 件が承認待ち、残りがその後ろで待機になった。
古い実行は承認しても main の最新の確認で止まり本番に出ないが、先頭から順に却下（Reject）しないと最新の実行の番が来ない。
却下が面倒で放置され、その間 HSTS（#386）やセキュリティヘッダー（#335）が本番に出なかった。

NatuEve_API の本番ジョブは `queue` を指定せず（既定の `single`）、新しい実行が来ると承認待ちの古いジョブが
`Canceling since a higher priority waiting request for deploy-production exists` で取り消される。承認者は最新の 1 件だけを承認すればよい。

## 決定

本番ジョブの `concurrency` から `queue: max` を外し、既定の `queue: single` にする。
新しい実行の本番ジョブがグループに入ると、承認待ち・待機中の古い本番ジョブは自動で取り消される。

検証ジョブ（`deploy-staging`）は `queue: max` のまま変えない。デプロイ直前の main の最新の確認（ADR-0003 決定 3）も変えない。

## 理由

- **本番に出るコードは変わらない**: 本番に出るのは、デプロイ直前の確認を通った main の最新のコミットだけである。
  この確認は `queue` の設定に関係なく効くため、`single` にしても古いコミットが本番に出ることはない。
  検証と本番は同じ実行の `github.sha` から出すため、検証したものと違うコードが本番に出ることもない（ADR-0003 決定 3）。
- **ADR-0003 が避けたかった事態は、起きても本番が止まるだけ**: 最新の実行の本番ジョブが、後からグループに入った古い実行の本番ジョブに取り消されると、
  残った古いジョブは承認しても確認で止まり、次のマージか最新の実行の再実行まで本番に出せない。誤ったコードが出るわけではない。
- **その事態はほぼ起きない**: 本番ジョブがグループに入るのは検証ジョブの後で、検証ジョブは `queue: max` で順に動き、最新でなければ失敗して本番ジョブを起こさない。
  古い実行の本番ジョブが最新の実行より後にグループに入るには、古い実行の検証ジョブが最新の確認を通った直後に次のマージが入り、
  そのうえ新しい実行の検証ジョブが古い実行の本番ジョブより先に終わる必要がある。起きたときは、ADR-0003 のとおり最新の実行を再実行する。
- **承認の手間がなくなる**: 承認者は最新の 1 件を承認するだけでよく、古い実行を 1 件ずつ却下しなくてよい。NatuEve_API と運用がそろう。

## 影響（結果）

### 良い影響
- 承認待ちは常に最新の 1 件だけになる。古い実行の却下が要らなくなる。
- 承認を待つ間にマージが続いても、承認する実行を探さなくてよい。

### トレードオフ・制約
- 取り消された古い実行は、Actions の一覧に `cancelled` として残る。
- まれに最新の実行の本番ジョブが取り消されたときは、手動で再実行する（`github.sha` は変わらないため、最新の確認を通る）。
- `single` で、承認待ちのジョブがグループの「実行中」として扱われるかは公式に書かれていない。NatuEve_API の実行で、承認待ちのジョブが新しいジョブに取り消されることを確かめた（2026-11-16）。
  このリポジトリでは、マージ後の実行で同じ動きになることを確かめる。

## 検討した代替案

- **`queue: max` のまま、古い実行を却下する**（ADR-0003 のまま）: 承認者の手間が残り、実際に放置された / 不採用
- **`cancel-in-progress: true` にする**: デプロイ中のジョブまで中断され、本番が中途半端な状態になりうる / 不採用
- **古い承認待ちを取り消すジョブを足す**: `gh run cancel` に `actions: write` が要り、Cloudflare のトークンを扱うワークフローに書き込み権限が増える。`single` で足りる / 不採用
