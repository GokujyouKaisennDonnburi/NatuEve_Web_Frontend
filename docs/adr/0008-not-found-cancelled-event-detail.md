# ADR-0008: 取りやめ済みのイベント詳細ページを 404 にし、API の `410` と `200` + `cancelledAt` を同じに扱う

- ステータス: Accepted
- 日付: 2026-11-26
- 関連: #473, ADR-0007, NatuEve_API#314, NatuEve_API ADR-0055（予定）

## コンテキストと課題

NatuEve_API#314 により、取りやめ済みのイベント（`cancelled_at` が設定されている）について、次の 2 つの API が `410 Gone` を返すようになる。NatuEve_API ADR-0054 の「詳細 API は取りやめ済みも返す」を置き換える（NatuEve_API ADR-0055 として起こす予定）。

- `GET /api/v1/events/{id}`（詳細）
- `GET /api/v1/events/{id}/report`（レポート）

ADR-0007 は、詳細 API が取りやめ済みも返す前提で「詳細ページは 404 にせず `noindex` にする」と決めていた。その前提がなくなるため、フロントの扱いを決め直す必要がある。

制約と前提は次のとおり。

1. **フロントと API のどちらを先にデプロイしても動かしたい**。API の変更前は `200` + `cancelledAt`、変更後は `410` が返る。
2. **`410` の本文の `error.code` は API 側で検討中**。本文にはイベントのタイトルや `cancelledAt` も入らない。
3. **主催者本人が開いても `410` になる**。
4. **Next.js の `notFound()` は 404 を返し、`not-found.tsx` には ID などを渡せない**。
5. 詳細 API は SSR の詳細ページのほか、詳細ページの再取得（`useEventDetail`）、参加申込の確定ページ（`useEventJoinConfirm`）、レポート投稿ページ（`report-post/page.tsx`）から呼ばれる。
6. 画面では取りやめを「削除」と呼んでいる（`EventCancelModal.tsx`）。

## 決定

**取りやめ済みのイベントは、API の `410` と `200` + `cancelledAt` を `getEventDetail` で同じ「取りやめ済み」にそろえ、詳細ページは `notFound()` で 404 にする。**

1. `getEventDetail`（`src/services/event.ts`）は、API が `410` を返したときと、`200` で `cancelledAt` が `null` 以外のときに、`status: 410` の `EventDetailError` を送出する。判定は HTTP ステータスと `cancelledAt` だけで行い、`410` の本文は読まない。呼び出し側は `isEventGoneError`（`src/lib/errors.ts`）で判定する。
2. 詳細ページ `/event/[id]` は `getEventDetailOrNull` で `404` と `410` を `null` にし、`notFound()` で 404 にする。「存在しない」と「削除された」は表示し分けず、`not-found.tsx` は両方に当てはまる文言にする。
3. 詳細ページを開いたまま再取得して `410` が返ったら、古い内容とレポートを消し、「このイベントは削除されました」を表示する（`EventGoneNotice`）。見出しは h1 にしてフォーカスを移し、タブのタイトルも差し替える。以降の再取得はしない。
4. 参加申込の確定ページとレポート投稿ページは、`410` をエラー扱いにせず（ログ・エラーの toast を出さない）、操作の代わりに「このイベントは削除されました」を表示する。戻り先は、詳細ページも 404 になるためイベント一覧にする。
5. `getReport`（`src/services/report.ts`）は `410` を「レポート無し」と同じく `null` にする。
6. ADR-0007 の `noindex`（`buildEventMetadata` の `cancelledAt` の分岐）は消す。取りやめ済みは `buildEventMetadata` に届かなくなるため。
7. MSW のモックは、取りやめ済みのイベントの詳細とレポートに `410` を返す。

## 理由

- **API の変更前後で同じ見え方にする**: 判定を `getEventDetail` の 1 か所に寄せると、4 つの呼び出し側が API のデプロイ順に関係なく同じに動く。
- **本文に依存しない**: `error.code` の名前は未定で、ステータスだけで判定できる。
- **404 で検索結果からも外れる**: 404 のページは検索結果から外れるため、`noindex` を別に付ける必要がない。取りやめたテストやスパムのイベントを検索に残さないという ADR-0007 の目的は 404 でも満たせる。
- **2xx を返さない**: 取りやめ済みのページを 200 で返すと、検索エンジンや共有リンクの OGP に中身のないページが残る。
- **表示し分けない**: `not-found.tsx` に ID を渡せず、表示し分けるには 200 で返すか独自の仕組みが要る。`410` の本文にタイトルも入らないため、分けても伝えられる情報が少ない。
- **再取得で `router.refresh()` を使わない**: サーバーの再描画とクライアントの Router Cache に表示の切り替えを任せることになり、`next start` や将来 Cloudflare 上でキャッシュを入れた場合（`unstable_cache` の `revalidate: 60`）は古い HTML が返りうる。クライアントの状態で確実に表示を切り替える。

## 影響（結果）

### 良い影響
- API とフロントのどちらを先にデプロイしても、取りやめ済みの詳細ページは 404 になる。
- 開いたまま取りやめられても、古いイベントの内容で申し込もうとしなくなる。
- 申込確定・レポート投稿で、取りやめ済みのイベントがエラーとして扱われなくなる。

### トレードオフ・制約
- 通知メールや共有リンクから来た人は、詳細ページで「削除された」ことを確実には知れない（404 の文言で「削除された可能性」を伝えるのみ）。ADR-0007 で避けていた点で、API が `410` を返す以上は受け入れる。
- 主催者も、取りやめたイベントの詳細ページを開けなくなる。
- 詳細ページは `unstable_cache` の `revalidate: 60` を指定している。現状の本番は OpenNext の incremental cache が dummy のため実際にはキャッシュされず、取りやめ直後から 404 になる（`docs/Deployment.md`「イベント詳細の SSR / メタデータ」）。`next start` や、将来キャッシュを入れた場合は、取りやめ後も最大 60 秒は詳細が表示されうる（#473 では変えない）。
- API を先にデプロイすると、フロントが対応するまで取りやめ済みの詳細ページはエラーページになる。そのため、マージとデプロイはフロントを先にする。

## 検討した代替案

- **「存在しない」と「削除された」を表示し分ける**: `not-found.tsx` に ID を渡せず、分けるには 200 で返すか独自の仕組みが要る / 不採用
- **取りやめ済みを 200 で返し、`noindex` を残す（ADR-0007 のまま）**: API が `410` を返すと中身がなく、2xx のまま空のページになる / 不採用
- **呼び出し側ごとに `410` と `cancelledAt` を判定する**: 4 か所で判定がずれやすく、API の変更前後で見え方が変わりうる / 不採用
- **再取得で `410` が返ったら `router.refresh()` で 404 ページに切り替える**: キャッシュの有無によっては古い HTML が返りうる / 不採用
